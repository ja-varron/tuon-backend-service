TUON AUTHENTICATION & AUTHORIZATION IMPLEMENTATION PLAN
========================================================

UPDATED ACCOUNT MODEL
---------------------

Tuon has two account-creation paths:

1. ADMIN SELF-REGISTRATION

The public registration page requires:
    Institution Name
    Email
    Password

After successful OTP verification:
    users.email_created_at = verification timestamp
    institutions row is created
    profiles row is created
    profiles.first_name = submitted Institution Name
    profiles.role = admin
    profiles.institution_id = newly created institution

2. INSTRUCTOR/STUDENT PROVISIONING

Instructors and students do NOT publicly self-register. They are created by an authenticated admin.

For both account types:
    profiles.institution_id = authenticated admin's institution_id
    profiles.role = determined by admin
    other profile information = determined by admin
    users.email_created_at = automatically populated by the system

The public signup flow therefore creates ADMIN accounts only.

1. CORE SECURITY MODEL
----------------------
Authentication answers: "Who is this user?"
Authorization answers: "What is this authenticated user allowed to access or change?"

Use two enforcement layers:
    FastAPI -> JWT authentication + role/institution/ownership checks
    PostgreSQL -> Row Level Security (RLS)

3. ADMIN PUBLIC SIGNUP
----------------------
Endpoint:
    POST /api/v1/auth/signup

Request:
    {"institution_name":"Example University","email":"admin@example.com","password":"..."}

Process:
    1. Validate input.
    2. Normalize email.
    3. Apply signup rate limiting.
    4. Check existing account.
    5. Hash password.
    6. Create users record.
    7. Generate short-lived OTP.
    8. Store only OTP hash in otp_flows.
    9. Send OTP.
   10. Wait for successful OTP verification before institution/profile completion.

Rules:
    - Public signup creates ADMIN only.
    - Server assigns profiles.role = admin.
    - Client does not submit institution_id.
    - Server creates institution from institution_name.
    - Never store plaintext passwords or OTPs.

4. ADMIN OTP VERIFICATION
-------------------------
Endpoint:
    POST /api/v1/auth/otp/verify

Process:
    1. Find active OTP flow.
    2. Check expiration.
    3. Check attempts.
    4. Verify OTP hash.
    5. Reject invalid/expired OTP.
    6. Increment failed attempts.
    7. On success, invalidate OTP, set users.email_created_at, create institution, and create admin profile.

Institution/profile creation should be one database transaction.

Result:
    institutions.institution_name = submitted institution name
    profiles.first_name = submitted institution name
    profiles.role = admin
    profiles.institution_id = newly created institution

5. OTP SECURITY
---------------
Require:
    - short expiration
    - maximum attempts
    - IP/account rate limiting
    - resend cooldown/rate limiting
    - OTP hashing
    - invalidation after success

Use 429 Too Many Requests when limits are exceeded.

6. SIGN-IN
----------
Endpoint:
    POST /api/v1/auth/signin

The same endpoint is used for admin, instructor, and student accounts.

Process:
    1. Validate input.
    2. Normalize email.
    3. Apply rate limiting.
    4. Find users record.
    5. Verify password hash.
    6. Verify account eligibility.
    7. Load profile.
    8. Create short-lived JWT.
    9. Return token.

Never return passwords, password hashes, OTP hashes, or internal database errors.

7. JWT AUTHENTICATION
---------------------
Use:
    Authorization: Bearer <access-token>

Minimum identity:
    sub = user_id

Role/institution claims may be convenience information, but the database remains authoritative for current authorization.

8. CURRENT USER
---------------
Endpoint:
    GET /api/v1/auth/me

Obtain the user from the JWT rather than accepting a user_id from the client.

9. ADMIN-CREATED INSTRUCTOR/STUDENT ACCOUNTS
----------------------------------------------
Suggested protected endpoints:
    POST /api/v1/admin/instructors
    POST /api/v1/admin/students

Only an authenticated admin may create these accounts.

Process:
    authenticate admin
        -> load admin profile
        -> require role = admin
        -> read admin institution_id
        -> create users record
        -> automatically populate email_created_at
        -> create profile
             role = admin-selected role
             institution_id = admin institution_id
             other information = admin-selected

10. NEVER TRUST CLIENT-SUPPLIED INSTITUTION
--------------------------------------------
The client must not choose an arbitrary institution for an admin-created account.

Instead:
    authenticated admin
        -> admin.profile.institution_id
        -> new profile.institution_id

11. ROLE AUTHORIZATION
----------------------
Required roles:
    admin
    instructor
    student

Basic model:
    admin -> manage users in their institution; create instructors/students; determine their profiles
    instructor -> instructor-permitted resources within institution scope
    student -> student-permitted resources within institution scope

Define detailed resource permissions only when those resources are implemented.

12. INSTITUTION AUTHORIZATION
-----------------------------
The institution is a primary authorization boundary.

Example:
    Institution A
        Admin A
        Instructor A1
        Student A1
        Student A2

    Institution B
        Admin B
        Instructor B1
        Student B1

Institution A users must not access Institution B data unless an explicit future authorization rule permits it.

13. RESOURCE OWNERSHIP
----------------------
For user-owned resources, verify the authenticated user's identity against the resource owner.

14. FASTAPI AUTHORIZATION DEPENDENCIES
--------------------------------------
Build:
    get_current_user()
        -> get_current_profile()
        -> require_role(...)
        -> require_institution_scope(...)
        -> require_resource_ownership(...)

15. RLS PRIORITY
----------------
Implement incrementally:

Phase 1: profiles
    Users can access their own profile where permitted.

Phase 2: admin-created accounts
    Admin can manage accounts belonging to the admin's institution.

Phase 3: course_enrollment
    Student access limited to own enrollment.

Phase 4: exam_papers
    Student access limited to own papers.

Phase 5: score_results
    Student access limited to own results.

Phase 6: feedbacks
    Student access limited to own feedback.

Phase 7: courses / exams / answer_keys
    Enforce institution and role-based access through relationships.

Test RLS independently from FastAPI.

16. DEFENSE IN DEPTH
--------------------
Protected request:
    HTTPS
      -> JWT validation
      -> current user/profile
      -> role check
      -> institution check
      -> ownership check
      -> PostgreSQL RLS
      -> protected resource

17. INITIAL ENDPOINTS
---------------------
Public:
    POST /api/v1/auth/signup
    POST /api/v1/auth/otp/verify
    POST /api/v1/auth/otp/resend
    POST /api/v1/auth/signin
    GET  /api/v1/auth/me

Protected admin operations:
    POST /api/v1/admin/instructors
    POST /api/v1/admin/students

Profile:
    GET   /api/v1/profiles/me
    PATCH /api/v1/profiles/me

Do not expose public signup endpoints for instructors or students.

18. HTTP STATUS CODES
---------------------
200 OK      successful OTP verification, sign-in, /me
201 Created newly created account/profile
400 / 422  invalid request/input
401        missing or invalid authentication
403        authenticated but not allowed
404        requested resource does not exist
409        account/resource conflict
429        authentication/OTP rate limit exceeded

Use a consistent error format:
    {"error":{"code":"ERROR_CODE","message":"Human-readable message","details":[]}}

Never expose SQL errors, stack traces, password details, OTP details, or internal implementation details.

19. RATE LIMITING
-----------------
Apply strict limits to:
    /auth/signup
    /auth/otp/verify
    /auth/otp/resend
    /auth/signin

Also consider limits for admin account provisioning.

                 |
                 v
             ADMIN SIGN-IN
                 |

                 JWT
                 |

        ADMIN AUTHORIZATION
                 |
          +------+------+
          |             |

    Create Instructor  Create Student
          |             |
          +------+------+
                 |
                 v
        Same institution_id
        as authenticated admin
                 |
                 v
          JWT AUTHENTICATION
                 |
                 v
       ROLE + INSTITUTION +
          OWNERSHIP CHECKS
                 |
                 v
           PostgreSQL RLS
                 |

        Protected Tuon Data

Implementation goal:
    Admin Signup
        -> OTP Verification

        -> Admin Sign-in
        -> JWT
        -> Admin creates Instructor/Student
        -> Institution-scoped Authorization

Only after this chain is secure and tested should broader application authorization be implemented.
